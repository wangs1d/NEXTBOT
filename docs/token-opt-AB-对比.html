三、逐项结论（优化点 1–5）

#1cognize 短路（死代码删除）
BEFORE / AFTER 均不存在 cognize 调用：main_chat 恰为 5 条 llm-route:: 路由调用，没有多余的第 6 条。 实证 createDefaultCognitiveEngine().cognize 的 LLM 分支确为死路径（DecisionHub 无条件接管）。 对 token 的影响 = 0（本来就没跑）；收益是移除不可达代码与潜在误调用风险。
#2routeTurnByLlm 同轮在途去重
本组 5 场景未出现真并发重复路由。AFTER S3 可见两条同会话 llm-route:: 记录（同输入 3039/3039、同输出 230/230）， 这是 routeTurnByLlmInner 内部超时/坏输出重试（结构化调用的可靠性机制），落在同一 Promise 内、不应也不被去重。 新增的 routeInflight 仅作为「同输入并发」的安全网，本组无 token 影响。
#3前缀缓存
BEFORE 缓存命中 22,795 tok / AFTER 仅 384 tok，差异巨大且不可复现 —— 归因 provider（MiniMax）服务端多副本随机命中，代码侧分层已正确。已记录，不改代码。
#4mood/topic 复用路由 aux
无代码改动（已验证本就生效）。AFTER S3 出现的 mood_inference + topic-extractor 是「任务面轮次 + aux 缺失」触发的设计内兜底； BEFORE S3 恰好落在 chat 面、aux 命中因而不发 —— 属路由分类抖动，非回归。
#5旁路审计补 actorId / sessionId
本次唯一可量化的净改进：BEFORE 有 4 条无归属（rolling_summary×3、user_profile_extract×1）→ AFTER 25/25 全部带 actorId/sessionId。 这是可观测性修复，让「谁花的钱」从此可归因（也才能算对预算闸）。

四、必须说明的两点口径

1) 单次运行的 LLM 抖动。两次 run 的 stage 组成并不相同（工具循环迭代次数、路由分类、前缀缓存命中都会随机）， 因此 estIn/apiIn 的 −20%/−27% 不能记为优化收益：main_chat_tools BEFORE 多跑了 3 轮、S3 在 AFTER 改走任务面。 要得到可归因的数字需多轮取均值，但即便如此，1–5 均非 token 节省型改动。
2) 工作树混有其他未提交改动。本次 stash 的 15 个文件里，除本任务改动外还夹带了 life-model 接线、画像净噪等旁支。 已确认对调用数/token 零扰动：life-manage 的工具 schema 由 openai-compatible-tool-loop.ts#L1076 常量注入（两相位一致）， store 接线与净噪均为零 LLM 路径。

五、一句话总结

这 5 个「疑似 token 滥用点」在真实链路上没有一个是真在省 token 的滥用：#1 是死代码、#3 在 provider 端、#4 本就在复用、 #2 的「重复」是内部重试、#5 只是记账归属。真正能砍 token 的方向在 #6（PLAN 输出封顶）——本轮按你的要求未做。 已完成的价值是：清掉不可达 LLM 路径、补上并发安全网、把审计归属补齐到 100%（能力零削减）。
