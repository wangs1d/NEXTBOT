设计要点

双通道分工

同一件主动代办事件走两条通道：对话流推消息摘要（必看、即时可达），面板记入动态台账（可回溯、可查详情）。动态卡不重复聊天气泡的职责，只做「代办结果账本」。

醒目的度

面板整体保持低饱和（延续现有分隔线设计语言），未读动态是唯一出现品牌色的地方：3px 竖条 + 8% 染色底 + 状态色 pill，对比产生醒目而非大面积高亮。看过即降级为灰阶。

呼吸提示复用

标题行的呼吸圆点复用面板现有的 breathe 动画语言（与今日安排区块的呼吸边框同款），有未读时出现，读完后消失——动画本身就是未读状态的一部分。

容量控制

默认最多展示 3 条，更早的进「查看全部动态」（后续可升级为独立动态页 / 时间线）。台账只增不减，但面板视图永远只保留最近与未读，避免堆积。

状态语义色

配送中 / 进行中 = 蓝（强调「正在发生」），已完成 = 绿，已改期 / 需注意 = 橙，异常 / 失败可扩展红。pill 只出现在未读与详情里，已读条目一律灰阶 pill。

天气的去向

面板组件删除，但 /weather/current 能力保留：天气继续由晨间简报承载，降水 ≥40%、寒潮、出行日程前等场景改由主动性管线按需推送——「需要时出现」而非「常驻占位」。

实现注记（动手改代码前需要处理的三件事）

  • ① 删除 _WeatherHeader 时保留定位上报链路：它目前是 onReportLocation（服务端位置缓存）的唯一触发点，建议把「定位 → 上报」挪到应用启动时静默执行一次。
  • ② 动态卡数据源：需要一个新的活动台账存储（Agent 每次主动代办完成时落一条记录，含类型 / 标题 / 摘要 / 状态 / 详情 JSON），可挂在 proactivity 的 delivery 环节。
  • ③ 未读判定：按「面板可见且条目已展示」置为已读（可在 RightSidePanel 挂载 2 秒后批量确认），对话内打开对应消息同样置为已读。
