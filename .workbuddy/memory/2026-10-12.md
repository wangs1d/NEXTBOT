1. **Markers 的 element 不能设 `position`** —— MapLibre 用 transform 定位；覆盖成 relative 会让内部 absolute 的标签包含块变成画布容器（实测 label 跑到 `x=117016`、逐字竖排）。改为「0×0 锚点盒 + 内层 `.wrap{translate(-11,-11)}`」。

3. **sprite `@2x` 变体路由** —— MapLibre 把后缀插在扩展名前（`/travel-basemap/fetch@2x.json?u=…`），缺这两条路由会 404 噪音。
4. 视野定位要在**路线请求之外**先做（`renderMap` 里落点后立即 `fitToSeq`），否则 OSRM 慢时地图停在默认 zoom，站点挤成一团。

## 用户问「每次现找不是长期方案，有没有更优的 / 上数据库 / 能随时更新数据照片」→ 旅行数据链路架构诊断

### 量化出来的三个硬事实
1. **照片覆盖率 3.4%**：`server/data/poi-cache` 11 个目的地 / **436 个 POI，只有 15 个有图**；59 处图片引用**全是外链、本地 0**。最热的大理（访问 5 次）36 个 POI 只有 4 个有图；马尔代夫 41 个、新疆 49 个**全无图**。
2. **根因：自动图片抓取只依赖一个不可达的源**。`travel-planning-service.ts:3465-3490` 的链路只有 Wikimedia geosearch + Wikimedia 文本搜索两段。实测 `commons.wikimedia.org/api.php` → `http=000 / 12.0s`、`zh.wikipedia.org` → `http=000 / 10.2s`（**完全不可达**）；而 `cn.bing.com/images/async` → `http=200 / 0.55s`（可达且快，`routes/http/travel-map.ts::fetchBingPhotos` 已在用）。→ **每次规划都为图片白等 10~12s 超时，然后拿到空数组**（3.4% 就是这么来的）。这是"没图"和"慢"的同一个根因。
3. **数据库早就写好了，只是没接线**：`skills/travel-planning/travel-poi-db.ts`（**523 行**）是完整的 SQLite 收敛层——meta/cities/pois/media_pois/media 四表 + WAL + schema 迁移 + `migrateLegacyJson()`（导入旧 JSON 后把目录改名 `*.migrated`）+ 单例 `travelPoiDb`。但**全仓库零引用**，`data/travel-poi.db` 从未创建。实际在跑的是 `poi-cache-manager.ts`（JSON 文件 + 内存，7 天 TTL + SWR）和 `travel-media-store.ts`（JSON + assets）两套并行，POI 与它的照片/评论靠 `poiKey = type:name` 字符串拼关联。

### 其他实测事实（避免下次重复查）
- 数据实际都在 **`server/data/`**（不是仓库根的 `data/`）：`tile-cache` 147M、`travel-media` 36M（assets 98 文件，主要是 `destcover<城市>` **目的地封面已本地化**）、`poi-cache` 11 份、`travel-plans` 32 份。
- 仓库根 `data/images` 2.5G 是**聊天图片**（dbg-img-* / qq_com），与旅行无关；`server/data/human-memory.sqlite` 13M 说明**项目里已经在用 SQLite**，DB 化不是新引入的技术栈。

### 建议方案（分级，待用户选落地范围）

## 用户否掉本地化设计「会导致安装包太大」→ 体积治理三件套

**先澄清事实**：安装包本来就不含媒体数据——`build-installer.ps1` 只拷 88K 的 `travel-knowledge`，其余 `data/*` 冒烟后被删。真实风险是 762MB 资产占本机磁盘 + 一旦有人整目录拷 `data/` 进 staging 就炸。

1. **写侧根治**：`travel-media-store.downloadImage` 出口统一收口 `normalizeDownloadedImage`（rotate + resize width 1280 + jpeg q76 mozjpeg）。一处改动，所有落盘路径受益；gif/svg 跳过，≤120KB 跳过，压不小则保留原图。实测大图 14.9x。
2. **打包防线**：`build-installer.ps1` 加断言——staging 出现 `travel-media`/`tile-cache` 直接 throw。**是断言不是清理**。
3. **存量瘦身**：`scripts/e2e/slim-travel-media-assets.mjs` 四阶段（计划落盘/写盘/回写 DB/删旧），幂等判据「宽≤1280 且已是 jpeg」。演练 762.4MB → 364.0MB（2.09x），748 条。

### 三个真坑（都已在脚本注释里钉死）
- **`travel-poi-db` 库路径是 `process.cwd()/data`**：脚本从仓库根跑会连上/新建**空库**，「改名写盘」照做、「DB 回写」全 miss → 悬空断链，且静态路由对不存在文件直接 404 **不报错，故障完全静默**。所有 e2e 脚本必须先 `process.chdir(SERVER)` + 库存在性断言。
- **media 行有两处 url**：`item_id` 是**原始 URL**（判重键，不随瘦身变），只有 `payload.url` 指向本地文件。回退/修复必须认这一点——第一版修复脚本按 item_id 找文件全部落空。
- **Windows GNU tar 把 `E:\...` 当 `host:path`** → 抽备份必须加 `--force-local`。

### 断链修复（新增 `scripts/e2e/repair-broken-travel-media.mjs`）
自检 `verify-travel-media.mjs` 报「本地 1233 条，断链 367」。修复策略（都不需要联网）：①`item_id` 原图仍在磁盘 → 重新压缩成合规尺寸 + 回写 url/sha256（365 条，既修链又保持瘦身）；②原图也没了 → 删行避免永久悬空（2 条，下次 refresh 按 originUrl 重抓）。结果**断链清零**。
- **备份坑**：`cp travel-poi.db` 会漏 WAL（4MB 未合并，备份出来只有 2MB 主库）→ 必须 `VACUUM INTO 'xxx.bak'`（1.18MB 一致快照）。
- 修完体积反而涨到 873MB（3088 文件）——瘦身留下的新旧并存，重扫生成新计划收尾。

### 真正的根因：压缩治不了体积，回收才是
重扫后计划仍显示「868MB → 489MB，699 条」，但**计划的 `from` 文件在 DB 里命中 0 条**——即这 699 张全是无人引用的旧原图。诊断清楚：
- media 表只引用 **1231** 个本地文件，**全部存在**（断链 0）；
- 磁盘却有 **3088** 个文件 → **1845 个孤儿 / 718.9MB**。

新增 `scripts/e2e/purge-orphan-travel-assets.mjs`：**移入 `.quarantine/<时间戳>/` 而非 unlink**（判定有漏时代价只是白占磁盘，不是功能损坏）。结果 **assets 873MB → 189.1MB**，断链仍 0，`test/travel-*.test.ts` 119/119。

**引用源必须穷举 5 处，漏一个就误删**：
1. media 表 `payload.url`（权威源）
2. `destination-covers.json` 的 `covers` 当前封面 URL
3. **同文件 `coverDirs` 是目录级路由** —— `resolveSuperseded` 把「该目录下任何文件的请求」都换发当前封面，所以这些目录里的文件即使不是当前封面也可能在服务，**整个目录受保护**（本次 6 个目录 6 份文件受保护，差 1 处就会删掉在服务的封面）
4. `server/data` 下所有文本文件里的 `travel-media/assets/...` 字面引用（行程快照烤死了本地 URL，367 条）
5. `assets/remote-cache/`：纯 `sha1(remoteUrl)` 抓取缓存，删了会重抓但走网络 → **默认不清**，需显式 `--purge-remote-cache`

**遗留**：`.quarantine/2026-10-12T09-29-39-885Z`（688MB）与 `travel-poi.db.bak`（1.18MB）待用户确认后删除；`travel-media-slim-backup.tar`（806MB）同理。

## 手机端「对话历史没保存」→ 本地存储落盘三缺陷根修（2026-10-12 23:43-23:55）
- 现象：手机端聊天记录重启后丢失（用户报「还是没有保存 本地持久化」）。持久化代码链路本身在（10-08 已接：saveMessage/listMessages/bootstrap），问题在 IsarLocalHistoryStore 的**写盘方式**。
- 三个叠加缺陷：①写盘非原子——`_flush()` 全量 `writeAsString` 直写 `private_ai_agent_store.json`，手机上滑杀进程落在写盘中途留半截 JSON；②启动判损坏即清库——JSON parse error → 备份后重建空文件，历史整库蒸发，release 下 debugPrint 全弃完全静默；③并发交错——`_persist` fire-and-forget，分泡定稿一帧多条并发 flush，同文件两次截断写互相踩（损坏/丢更新）。附带发现：listMessages 重组漏 summaryCard（重启后折叠卡消失）+ 单条解密失败炸整个加载链。
- 修复（isar_local_history_store.dart）：①原子落盘 tmp+rename（POSIX 原子；rename 失败退回直写）；②`_flushQueue` 写盘串行链（快照在链内取 + catchError 防链毒化）；③listMessages 逐条容错（单条损坏只跳过该条）+ 补回 summaryCard。
- 验证：dart analyze 0 error（flutter test 本机不可用，编译门即 analyze）；重打 APK（build_apk.ps1 -HttpBase http://159.75.52.2:3000，3m22s，SHA1 3CE1BA91…）；四层验证——libapp.so 三 ABI 均含新增字符串「写盘链异常/跳过损坏消息」（中文在 AOT 快照是 **UTF-16LE**，grep 中文须按此编码，UTF-8 永远 MISS——排查手法备忘）、159.75.52.2×11、127.0.0.1:3000 回落 0 命中。
