## 多轮 tool schema 是否「残留」——机制澄清 + 根因

**用户问「多轮对话中 tool schema 一直残留在上下文」，严格说不准确**：
- `tools` 数组**不进 messages/history**，是每轮请求的独立字段，不存在「残留」。
- 但**工具可见集在会话内单调累积**：首轮 BM25 可见 33 个 → 会话并集累积到 45（上限 `SESSION_TOOLS_UNION_MAX=48`）。所以每轮发出的 schema 越来越大，体感等同"残留"。
- history 里确实有工具调用结果，那是 OpenAI 协议必需，不是本问题。

**真正的根因不是「工具多」，是「tools 数组每轮都在变」**：
1. `lane-tool-sets.ts` 已有完整三级架构（静态 core + 延迟目录 + `<tool_request>` 请求卡），注释明写「每轮重算打爆前缀缓存 → 选一种暴露模式然后不动」。**机制不缺**。
2. 但实现上叠加了两层动态：`CHAT_LANE_CORE_NAMES` **20 个** + 域预载（BM25 `domainVotesForQuery`/`priorDirectMatchesForQuery`）**+13 个** = 首轮 33 个；再经 `stabilizeToolOrderForSession` 单调并集 → 45 个。
3. **域预载每轮不同 + 并集逐轮追加 ⇒ tools 数组逐轮变化 ⇒ 与「静态常驻保缓存」的设计意图直接相悖。**

**实测证据（缓存）**：工具集稳定的评测会话 hit=10,920 / apiPrompt=11,084（**命中 98.5%**）；我 probe 的会话工具集 33→38→45，**hit 恒为 128（≈1.2%）**。今天 main_chat_tools 整体缓存命中率仅 **29.8%**。

**方案（会话级锁定 tools 数组）**：
- L0 常驻层：core（20 个，或收敛到 12~15）写进 tools 数组，**整会话逐字节恒定**；
- L1 按需层：域预载/检索命中**不再并入 tools 数组**，走已有的 `<tool_request>` + `deferredCatalog` 通道下一波注入（或降级为写进 history 尾部的文本提示）；
- 取消会话单调并集（改为波内临时追加、波末回收）。
- 关键不变量：**tools 数组整会话不变** → 前缀缓存稳定命中。

**收益（K=0.385，单工具均值 433 ch）**：
| 工具数 | schema | token | 说明 |
|---|---|---|---|
| 45 | 19,480 ch | 7,494 | 现状会话后期 |
| 33 | 14,285 ch | 5,496 | 现状首轮 |
| 20 | 8,658 ch | 3,331 | 方案（保留 core） |
| 12 | 5,195 ch | 1,999 | 方案（激进收敛） |

- 单次 raw prompt 省：短会话 2,165 / 平均(~38个) **2,878** / 长会话 **4,163** token。
- 缓存命中 29.8% → 预期 60~70%（有 98.5% 的实证上界），按缓存 0.2x 计价则计费系数 0.762 → 0.48（**-37%**）。
- **综合计费口径降幅 50~65%**；今天 main_chat_tools 真实 API prompt 124,212（17 次）→ 省约 6~8 万 token 当量。
- 附带收益：工具数从 45 降到 20 落在前沿「~50 个 → 84-95% 准确率」区间内，准确率方向也是正向。

**风险/权衡**：域预载移出 tools 后，模型需多一轮 `<tool_request>` 才能拿到域工具 → 延迟上升（与去路由化那次同类权衡）。**建议灰度**：先做「并集取消 + core 锁定」，保留域预载兜底，测一轮再决定是否把域预载也移出。

## P0：绿色版（zip）在新用户机器上「后端永远拉不起来」根修

**现象**：把 `D:\Nextbot`（Inno 安装后目录）压缩成 zip 发给用户，用户解压后「界面能开但连不上」，本机测试却一直正常。

**根因（已对照实验坐实）**：`services/voice-dialogue/adapters/openai-llm-adapter.ts` 在**构造函数**里 `if (!key) throw new Error("OpenAI API key is required")`。它被 `create-app-services.ts:827` 在 bootstrap **同步装配路径**上无条件 `new` 出来 → 缺 key 时 throw 变成 `uncaughtException` → **整个服务进程 abort（退出码 134），3000 端口从未监听**。
- byok 捆绑形态下，key 的唯一来源是客户端注入的 `%APPDATA%\PrivateAgent\config.env`（`LocalRuntimeManager.ensureRunning` 把它并进 `Platform.environment` 传给 node）。**新用户首启这个文件根本不存在** → 注入空配置 → 必崩。
- 对照实验：旧 dist 零 key → `HTTP 000` + `[FATAL] uncaughtException: OpenAI API key is required`；新 dist 零 key → `HTTP 200`（冷启动 16.2s）。

**为什么本机永远测不出来（三重假象，务必记住）**：
1. 本机 `%APPDATA%\PrivateAgent\config.env` 里躺着 9/21 配的 `OPENAI_API_KEY`；
2. **WorkBuddy 会话的 shell 环境本身也注入了 `OPENAI_API_KEY`**，任何手工起服务的测试都自带 key；
3. `build-installer.ps1` 4.5 冒烟显式 `$env:OPENAI_API_KEY='sk-smoke-...'` —— 门禁自己把坑绕过去了。
另：`ensureRunning()` 第一行 `probeHealth()` 命中 3000 就直接 return true，所以「exe 到底有没有拉起 runtime」本机从未真正验证过。

**修复**：
1. `openai-llm-adapter.ts` 改**调用期校验**：构造只保存 key、`client` 在有 key 时才 new（否则 null），新增 `isConfigured()`、`requireClient()`（缺 key 时在这里 throw，错误语义不变）。
2. `create-app-services.ts` 装配后 `if (!openaiLLMAdapter.isConfigured())` 打 warn「语音通话 LLM 暂不可用，填 key 后重启即恢复」（与 alipay-bot 降级提示同风格）。
3. 已 `tsc --noEmit` 0 错 + `npm run build` 通过；`server\dist` 已 robocopy 同步到 `D:\Nextbot\runtime\dist`（装机包 adapter 已确认无构造期 throw、含 requireClient）。

**新增诊断工具**（随包分发，放 exe 同级双击）：`scripts/release/diagnose-runtime.ps1` + `scripts/release/诊断后端.bat`。七项检查：isBundled 两件套 / 运行期依赖完整性（文件数低于 20000 判解压不完整）/ 最长路径 vs MAX_PATH / MOTW / 3000 占用 / **按客户端方式冷启动实测**（读 config.env 注入、量耗时、匹配 FATAL 原因）/ 客户端 runtime.log。报告落 `runtime-diagnose-report.txt`。

**写 PS 诊断脚本的两个坑**：
- **PS 5.1 的 `ProcessStartInfo.EnvironmentVariables` 是 null**，索引赋值直接抛 `NullArray`（且会让环境块异常，制造退出码 134 的假失败）。要注入变量就写 `$env:XXX='...'` 让子进程继承，别碰 `EnvironmentVariables`。
- **诊断者自己环境的 `OPENAI_API_KEY` 会泄漏给被测进程**，把「没 key 就起不来」这个根因完全掩盖。脚本必须先 `Remove-Item Env:OPENAI_API_KEY` 等 7 个模型变量，再注入 config.env。

**环境事实变更**：`D:\nodejs` **已不存在**（记忆里多处引用作废）。当前 Node 24 在 `C:\Program Files\nodejs\node.exe`（better-sqlite3 按该 ABI 编译，可正常 open `:memory:`）。
