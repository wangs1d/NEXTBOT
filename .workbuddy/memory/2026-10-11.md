## 票务邮件「规则命中」可靠性评估（答疑，无代码变更）
- 定性：**高精度、低召回**的保守策略——方向对，不是全覆盖。与财务账单解析器同一哲学（`finance-bill-file-parser.ts` 开篇明写「确定性解析、零 LLM；用 LLM 抽取既浪费 token 又可能编造/漏记」）。
- 三层结构（`mail-schedule-extractor.ts`）：粗筛 `isTicketLikeMail` → ① ICS 附件直取（`ics-attachment`，最可靠）→ ② 模板正则 `MAIL_TICKET_RULES`（脆弱点）。同一封邮件只走一条规则（`break`），退票/改签在购票之前。
- **误检防线厚**（所以敢自动写日程）：`subjectRe` 具体 + `parse` 硬校验（缺字段返回 null）+ 时间闸 `MATERIALIZE_MIN_LEAD_MS` 只建未来 + `matchKey` 幂等。故误检概率极低。
- **漏检代价被兜底**（`create-app-services.ts:5094-5111`）：解析失败 `ticketReport=null` → `suppressMailInterrupt=false` → importance≥high 仍有泛化「邮件：xxx」当场提醒（只是不建结构化日程）；normal 静默落库。
- **真实脆弱点（会失准的地方）**：① 正文纯图片/HTML-only 卡片邮件 → `bodyText` 无字段 → 全漏（最大风险）；② 发件人域白名单仅 8-10 家，小众航司/企业差旅/代理出票预筛即跳；③ 时间格式假设窄（无年份「10月15日」、斜杠日期漏；多段/中转航班只取首个航班号；首个 `HH:MM` 可能取到非起飞时刻）；④ 航线正则要求「站/机场 至 到」连接词，缺连接词丢 location（title 仍建）；⑤ **无漏检度量**——代码注释自认「LLM 兜底层留待规则层跑出漏检率数据后再接」，即当前不知道真实漏了多少。
- 提升阶梯（不推翻现方案）：A 低成本扩面（补域/补时间格式/HTML-only 剥文本）→ B **加「漏检指示灯」**（`isTicketLikeMail=true` 但 `drafts=0` 时计数/日志，产出真实漏检率）→ C 有边界 LLM 兜底（仅「预筛命中+规则失败」时调一次结构化抽取，结果仍走同一硬校验）。B 是 C 的前置条件。

## 03:37 事故定性：问「现在几点」把模型的决策自述当正文输出（截图 4 泡）

现象：用户问「现在几点」，助手连发 4 泡：①（用户问现在几点，根据规范必须调用 clock.getcurrenttime，禁止臆测。）

③ 直接调用。王哥，现在是 … 贵州兴义这边的时间。 ④ 这么晚还没睡?

定性（四层，已逐层在源码核实）：
1. **触发=prompt 自相矛盾**。默认 `promptMode=minimal`（runtime-kernel.resolvePromptMode 默认 minimal），
   此时 system = `buildSessionSystem()`（runtime-kernel.ts:588）："Current time is always in context
   (【当前时间】block) … **never call a tool for the current time**"；而 clock 工具 schema
   （builtin-chat-tools.ts:1081）写着"**【强制调用规则】**用户询问时间…**必须调用本工具**"（第 2 泡的
   「强制规则要求」「时区/城市」逐词出自这段描述）。另外 gateway/forced-tool.ts:49 真的强制
   `tool_choice=clock.get_current_time`，lane-role-guidance.ts:94 又是"不调工具也不反问" → 同一上下文
   三四种口径。模型先自述一遍权衡再执行。
   注意：minimal 分支（prompt-builder.ts:195-209）**不会**追加【消息时间戳】【时钟与位置】，所以非
   minimal 路径的「不要调用工具查当前时间 vs 必须调用 clock.*」是同一矛盾的另一种版本。
2. **泄漏路径=过程话（preamble）透出，不是 reasoning 通道**。`consumeNormalizedStream` 只把 content
   推 onContentDelta，reasoning 只累积不 emit（客户端也没有渲染推理的入口）→ 这段必然来自 content。
   tool-loop 在 `finishReason === "tool_calls"` 分支把 fullText 当**前导话**透出
   （openai-compatible-tool-loop.ts:2676-2686），这是设计允许出站的过程话，只是内容是一段内部权衡。
3. **净化三道全漏**：前导话只过 stripInlineThinkBlocks（think 标签）/ stripInternalControlTags
   （[话题切换]/[STOP]）/ createStreamMetaSentenceFilter（需单句 ≥2 个「对话脑/执行脑/规划任务…」）。
   出口风格闸的 `meta_narration` 只扫**括号段 + 任务态词表**（本轮主任务/profile_update/turnIntent…）：
   第 1 泡有全角括号但词表不匹配，第 2/3 泡根本没括号 → 全放行。**词表只覆盖"任务态复述"，不覆盖
   "我该不该调工具"的决策自述** —— 这是闸家族现有的缺口，不是新 bug。
4. **展示放大 + 无法撤回**：分泡器 bubbleMode（句末标点/换行切泡、maxBubbles=4）把同一段文本切成
   4 条独立绿泡；且 ws 收口只在 `residual` 非空时才补推/替换（chat-user-message.ts:1429-1462）——
   **纯删除型净化 residual="" → 整块跳过，不会打 finalTextReplacesStream**，客户端永远保留污 染气泡。
   推论：**出口闸修好了用户也照样看得到**；这类净化必须做在**分段器之前**（onDelta 咽喉），
   不能靠收口替换。

附带发现（潜在）：`CLOCK_TOOL_SYSTEM_SUFFIX_MARKER = "【时钟】"` 与后缀实际首段"【时钟与位置】"不匹配
