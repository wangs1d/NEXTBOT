### 关键架构结论（对 NEXTBOT 有参考价值）
- 三组件模型：前台 Agent（实时语音对话 + 轻量工具）/ 编排运行时 Orchestration Runtime（任务状态、权限、事件路由、结果投递，不是推理协调 Agent）/ 后台 Agent（ACP/A2A 接入的办事 Agent，如 OpenCode、Qwen Code、Kimi Code、Codex、Claude Code）
- Gateway 是服务化运行形态（应用装配 + 网络接入），不是第四个组件；客户端通过 Gateway Client Protocol 接入
- `spawn_thinking` 永不阻塞；每 owner 一次只发一个 Task 到 BackendPort，FIFO 队列
- Task 状态机：queued → running → delegated → finalizing → completed，另有 cancelling/cancelled/failed
- 记忆分两份 Markdown：`USER.md`（用户长期个性化覆盖，可作为行为指令）/ `MEMORY.md`（持久事实，绝不作指令）；`ASSISTANT.md` 只存实例人设
- 依赖方向硬约束：前台工具不得导入后端适配器；Gateway 源码不得导入 UI 组件
- 座舱基准 134 case：混合执行任务成功率 91.04%（直接 72.39%、全委派 80.60%），延迟降 26.73%/30.91%

### 与 OpenAI 架构的对比结论（重要，NEXTBOT 选型参考）
- 分层 idea 确实 OpenAI 先示范：`openai/openai-realtime-agents` 的 **Chat-Supervisor** 模式（chatAgent=realtime-mini 做对话，supervisorAgent=gpt-4.1 做工具/推理）。
- 但 Chat-Supervisor 是**同步阻塞**的单一 turn：前台说"稍等"→转发→supervisor 跑工具→返回→前台念出，README 自述 ~2s 延迟，任务期间对话停摆。
- Qwen-Audio-Agent 的实质差异：①`spawn_thinking` fire-and-forget 异步；②后台是 **ACP/A2A 接入的真实 Agent 进程**（OpenCode/Codex/Claude Code…），不是"更强的文本模型"；③有显式 Orchestration Runtime（确定性代码，不是模型推理）管 Task 状态机/权限/投递；④语音打断 ≠ 任务取消、执行完成 ≠ 结果播报（等安全窗口）。
- OpenAI 侧也有异步原语（Responses background mode、Agents API sessions/turns 可 steer），但公开参考架构里没跟 realtime 语音链路缝在一起。

### 前台人格/记忆的归属（关键设计）
- **是 qwen-audio-agent 自己的，与后台 Agent 完全隔离且刻意不互通。** 架构文档原文："后台 Agent 不接收前台人格、长期记忆或最近聊天历史"。
- 三份文档按**「是否具有行为权威」**区分（不是按主题）：`ASSISTANT.md` 实例人格（助手不可用 memory 工具改它）／`USER.md` 用户偏好覆盖（有行为权威，可覆盖 ASSISTANT.md，服从当前话语）／`MEMORY.md` 持久事实（绝不作为行为指令）。另有 `notes` 列表（条目数据，绝不写进偏好/事实记忆）和独立 `knowledge/` 知识库。
- 跨边界只传**一条自包含的自然语言 objective** + 协议原生附件；前台模型必须先把指代（"继续那个页面"）解析成自包含指令，ASR 原文不作第二份描述附加。
- 启示：换后端（OpenCode→Codex）人格不变；代价是后台不知道你是谁/聊过什么。

### 对「前后台隔离」的批判与 NEXTBOT 的修正方向（核心结论）
- 用户质疑：完全隔离 → 语音通话不真实、无法共享记忆/人格。这个批评**部分成立**。
- **为隔离辩护的一面**：后台从不直接对用户发声，结果永远由前台重新说出 → 人格一致性其实有保证；后台 Session 按 `qwen-audio-agent:<owner>:backend` 持久 → 后台自己也在积累记忆。所以不是"失忆"，是**两个脑子**。
- **批评成立的一面（真实的漏点）**：①执行层不知道你是谁，产出物（邮件/代码注释/文案）是通用 AI 腔，不是 NEXTBOT 的 playful「你」腔；②后台学到的项目约定不回流到前台，前台没法自然地聊那件工作；③指代消解失败时前台只能派发模糊 objective，后台猜错。
- **作者为何仍选隔离（关键）**：USER.md 具有**行为权威**（是用户授权的指令材料）。整份转发给有工具权限的后台 = 开提示注入口子（"以后别问我权限了" → 进 USER.md → 后台执行）。所以文档写明记忆"不能授权跳过权限检查"。另外后端异构 + 上下文成本也是原因。
- **NEXTBOT 不应照抄**：Qwen-Audio-Agent 的取舍是"开发效率/安全优先"（后台全是 coding agent），NEXTBOT 是伴侣型产品，**关系连续性就是产品本身**，缝不能漏。
- **提出的修正方案**：把「有没有行为权威」这条切分线从前台内部延伸到前后台之间 ——
  - 只让**描述性**内容过界（MEMORY.md 事实 + USER.md 里的称呼/风格/项目背景），生成一份**只读、无行为权威的用户画像投影**随 task 下发。
  - **指令性**内容（USER.md 里的默认做法、权限豁免诉求）绝不过界，留在前台。
  - 反向补一条**执行事实回流**通道：后台完成后的关键事实经精简写回前台 MEMORY.md。
  - 一句话：**只让「描述」过界，不让「指令」过界。**
- 这个思想其实 Qwen-Audio-Agent 已有雏形（USER.md vs MEMORY.md 就是按行为权威切的），但它只用在"前台内部"，没敢延伸到"前台↔后台"。

## 排查：答完称呼后又"回到正事—周末方案 A/B/C？"是哪个模块导致的

案例：actor 2378709729@qq.com，2026-10-09 18:35 轮「你应该叫我什么？」→ 答称呼后主动接「那回到正事——周末安排挑好了吗？方案 A（万峰林+马岭河）/B/C？给个准信我就把时间和闹钟一起钉死」。

结论：不是任何"主动/外发"模块，是**主模型在对话面续自己抛出的未答问题**，素材来自三处：
1. `external-model/chat-thread-store.ts` 的滚动摘要区（`[session-recap]`/`[关键钉]`，role=assistant，常驻 messages）。该 actor 的 recap 里逐字写着「此前请求规划10月10日(周六)和10月11日(周日)附近游玩路线，尚待确认范围、偏好、游玩天数及交通方式，agent 尚未给出路线」→ 直接读成"我还欠着一件事"。
2. 上一轮 assistant 原文（"方案 A/B/C？给我个准信"）就在 messages 里，未获回答即续问。
3. 跨会话 openLoops 双份持久化：`agent-memory-sync.json` 的 `session_epitome.openLoops` 与 `short-term-task-stack.json` 的 `conversationMemory.openLoops` 都有「帮我规划这个周末附近游玩的路线」（10-08 写入，7 天 TTL 未过）。注入时还带 `agent-core.ts:1776` 的「管家提示：…可主动提议『要不要我到点提醒你』」。但本轮实测未注入：recall-gate 未触发 → `suppressNarrativeRecall=true` 抑制【上一会话待办】；STM 焦点判 topic_switch → open-loops 行不注入。

已排除（实测验证）：
- 追问锚点 followUpAnchor：今天的"语义化重写"已改为 L1 路由 `understanding.reference` 驱动。跑 `server/test/tmp-probe/probe-turn-understanding.ts`（真实路由探针）：「你叫我什么？」→ chat，understanding=undefined（零注入），recall-gate=off。旧词表判定把该句锚到上一条旅游回复的路径已断。
- scheduleSnapshot / travelState 注入：同因 understanding 缺省而未触发。
- proactivity 主动模块（hub / 顺嘴搭车 turn-aside 是括号旁注形态 / GoalPlanner awaiting_confirm）：与本条无关。

可下手的位置（未实施）：①`conversation-rolling-summarizer.ts` 提示词禁写"尚待确认/尚未给出"类未结项（改写为中性事实）；②`session-epitome.ts` open loop 关闭条件（settle 需助手回复与条目 bigram≥0.45，"我应该叫你主人"永远清不掉该条）+ 新话题轮不注入；③`lane-role-guidance.ts` chat 面公共块补"用户聊别的事时不许把旧话题拉回"；④`reply-style-guard.ts` 加跨话题续问检测（回复含"回到正事/回到刚才"且与上轮追问对象零重叠 → 删句），符合本项目"prompt 说不听就程序层执法"的既有哲学。

## 灵动岛隐藏规则扩展：前台窗口最大化盖岛时也隐藏 + 顶边唤出（用户拍板）

- `dynamic_island_window.h`：新增 `kPeekTimerId=4`、`IsForegroundCoveringIsland()`、
  `UpdateTopEdgePeek()`、成员 `peek_active_` / `peek_last_in_zone_ms_(ULONGLONG)`。

## 21:45 诊断：MiniMax 语音回复慢 —— 主因是本地未做流式下发
- 结论：不是服务端慢，是本地侧少了流式。上游 MiniMax realtime 的 `response.audio.delta` 是逐段到达的（`MiniMaxRealtimeSession.onAudioDelta`），但 `voice-dialogue/minimax-realtime-service.ts` 的 `PersistentRealtimeClient.installHandlers` 把 chunk 全聚合进 `t.audioChunks`，等 `response.done` 才 `settle` 返回整段音频；`voice-duplex/minimax-duplex-session.ts` 的 `emitTurnOutput` 再 `pcmToWav` 打包成**单个** `tts.chunk` 一次性下发。→ 用户听到第一个字 ≈ 整轮生成时间（3~5s），而非首包（1.3~2.4s）。`emitTurnOutput` 自己已打 `⚠ 首包后又等了 xxxms 才下发，这段是纯等待` 警告。
- 协议层其实支持流式：`voice-duplex/protocol.ts` 的 `tts.chunk` 带 `seq`、且有 `tts.start/chunk*/end` 三件套；只是实现走成了单块整轮。
- 客户端也拦着：`client/flutter_app/lib/core/services/tts_player.dart` 是「整段 base64 → decode → 写临时文件 → DeviceFileSource 播」（Windows 因 BytesSource 崩溃强制走临时文件），不支持边收边播。→ 流式改造需两端一起动。
- 次级本地延迟：`endpoint-detector` 尾部静音 `VOICE_ENDPOINT_SILENCE_MS` 默认 550ms；上行分块节流 `MINIMAX_REALTIME_INPUT_PACE_MS` 默认 4ms（3s 音频≈120ms，可设 0）。
- 架构限制：MiniMax realtime 不支持 server_vad（下发 turn_detection 被忽略，必须手动 commit），故断句只能靠本地 VAD，无法省掉那 550ms。`maxResponseOutputTokens` 默认 `"1024"`（字符串），偏大 → 语音偏长，可压到 256~512 强制短回复。
- 待定：是否动手改流式（服务端 `PersistentRealtimeClient` 暴露回合内 audio delta 回调 + `MinimaxDuplexSession` 逐块发 `tts.chunk`；客户端加 PCM 流式播放器）。

## 23:2x 调研：主流 agent 如何应对「模型从摘要里翻旧账」（对照项目现状）
- **主流共识：改摘要的法律地位，而不是加提示约束**。摘要只做**指针/索引**，事实来源必须可回溯到原始 episodic 记录（带时间）；被压缩掉的原文仍可检索，但**不常驻上下文** → 模型想提旧事必须显式检索，"检索动作"本身就是一道闸。
- 四条主流做法：
  1) **三层记忆（Letta/MemGPT 正统）**：Core memory（小块结构化常驻）／Recall memory（完整历史，按需 `conversation_search` 拉**原文+时间**）／Archival（长期知识）。
  2) **存结构化事实而非自由摘要**（Zep/Graphiti bi-temporal、readpipe）：`llm.summarize()` → 换成 `llm.extract(schema)` 带 confidence；bi-temporal 的 valid_from/valid_to，冲突 supersede。理由是**摘要会 compounding hallucination**（幻觉写进摘要后升级为高置信记忆）+ 丢细节 + 丢时间顺序。
  3) **时间敏感状态类事实给短 TTL + confidence decay**：「好饿/在忙/心情」属瞬时状态，不该进跨会话长期记忆。
  4) **摘要 prompt 纪律（最弱一环，OpenAI cookbook）**：temporal ordering 保留时间戳、superseded 显式标记、不确定标 UNVERIFIED。
  5) durability gap（moltbook）：摘要是「重建的叙事」而非事件日志，会合并不同时刻的事件、丢因果顺序 —— 正是"旧事当现事"的根因；正统解法是 event log 而非 summary（代价：存储与推理成本）。
- **项目现状对照（关键发现）**：
  · Core 层已有（档案事实权威源 `structured_facts` + `workingMemorySummary`）✓
  · Episodic 当日已有（`journalRecall` 块格式 `[今天 hh:mm·角色] 原文`）✓
  · **按需检索工具已存在且已装配**：`tools/memory-recall-tools.ts`（`registerMemoryRecallTools` / `MEMORY_RECALL_CHAT_TOOLS`，`bootstrap/create-app-services.ts:337`），返回原文 + `time`（`new Date(t.ts).toISOString()`）—— 即 Letta 的 `conversation_search` 等价物；**但描述限定"当前会话"**，不覆盖跨会话历史 ⚠
  · **跨会话历史 = recap 自由文本常驻注入**（唯一没有按需检索路径的一层）← **病灶**
- 结论：正统解法不是我上一轮提的 A(剔除)/B(回复后校验)，而是把 recap 从「可引用的叙述」降级为「目录/索引 + 指针」，细节走召回工具按需取（需把工具范围从当前会话扩到跨会话），状态类事实加 TTL。

## 23:48 设计澄清：分类索引为何不污染（用户质疑「索引行带上不还是污染吗」）
- 结论：污染 = 原话可引用 + 相对词漂移 + 年龄不可见 三者同时成立。分类索引在**写入端**逐项剥除，不是注入端打补丁：
  1) 摘要器写入时先分类「瞬时状态 vs 持久事项」——瞬时（好饿/在忙/心情）只在在途窗口（小时级）留索引，**超窗根本不进上下文**，仅存可检索层（主流第3条：状态类短 TTL，落点在摘要器不在注入器）；
  2) 持久事项行只有冷目录语义（无原话/无相对词/行首绝对日期），模型最坏说「你昨天提到X还没定」——这是对的，不构成污染；
  3) 索引可见≠允许主动提：跨天未闭环行写入时策略位降为「勿主动提」，主动提及走 temporal-admission 闸（同一套 kind 窗口）。上下文层管「知不知道」、闸管「能不能说」，正交。
- 待用户确认后落地：摘要器双段输出（索引段常驻/细节段可检索）+ 写入时 TTL 分类 + 策略位字段。
