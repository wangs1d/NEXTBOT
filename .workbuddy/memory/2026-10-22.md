## 前缀缓存真根因：消息头部三处可变（2026-10-22，比 tools 更上游）
- 结论更正：**冻结 tools 并不能让跨轮缓存命中**。实测 hit 恒为 128/≈10,000（1.2%），而同轮 wave 间命中 99%。`PREFIX_WATCHDOG` 只比 tools/system 两段，看不见 messages 内部 → 这就是这条劣化长期没被发现的原因。
- 逐条比对定位（临时探针，已删）；三个源头全部在**消息头部**：
  1. `tailDynamicContext` 追加到最后一条 user 消息尾部；该消息落库时是干净的，下一轮作为历史出现内容就变了 → `diffAt=1`，从第一条 user 起整段作废。
  2. `[session-recap]` 以 system 消息插在 system 之后（index 1），内容逐轮更新 → `roles=system,system,...`、`diffAt=1`。
  3. 历史被折叠/滚动摘要后**变短**（msgs 12→5，`SHRINK`）→ 上一轮请求不再是本轮前缀。
- 可复用诊断：`PREFIX_DEBUG=1` 起服务，`data/prefix-dbg.log` 逐请求输出 `diffAt`（第几条消息开始不一样）+ tools/system/history/tail 四段指纹。
- 未做（待开工）：把消息头改成 append-only（尾部动态上下文改为「最后一条 user 之后的独立消息」；recap 不插头部或冻结首轮字节）。预计 hit 24%→80%+，计费当量再降六成。**当时被 MiniMax 余额耗尽（HTTP 402 insufficient balance）挡住，无法 A/B 验证，故未动。**

## 消息头 append-only 收尾：四处真根因（2026-10-22 凌晨）
- **目标达成**：`main_chat_tools` 命中 5,888/9,454（59-62%）→ **8,320/9,449~9,856（86.8% / 84.4%）**；线程结构从 n=2→4→7→10（每轮插一条重复 user）修成 2→3→4→5→6→7（一轮一 user 一 assistant）。
- 用 `PREFIX_DEBUG=1 PREFIX_DEBUG_FULL=1` 逐请求 dump（`data/prefix-dbg.log` + `[trim-entry]/[writeback]/[recap-build]` 日志）定位到四个真因，**原先怀疑的「尾巴拼进 user 消息」只是第四位**：
  1. **回写边界错**（最致命）：`llmViewTurnBoundary` 取「最后一个活对象下标」，但视图会为剥 `__ts`/clientMessageId **克隆本轮 user 消息** → 从本轮 user 起整段被当成"视图新增"回写，每轮往线程多插一条一模一样的 user。改为按**视图长度**定界（`llmViewAppendBoundary = llmView.length`），只回写循环真正追加的。
  2. **轮内脚手架入史**：域卡+工具守则（8,266 字符≈3,200 real tokens）、时间轴块、请求卡/出口闸转向指令都 push 进同一数组 → 轮末写回落库，每轮重发且位置漂移。新增 `external-model/turn-scaffold.ts`（WeakSet 按对象身份标记，零字段污染），写回时跳过。
  3. **裁剪预算双重失真**：`estimateTokens = 中文字数*1.5 + 英文词数*0.25`——中文高估 1.5-2 倍、英文低估 2.5 倍。6,042 字符的身份 system 被估 5,234，**单条吃掉 MAX_CONTEXT_TOKENS=6000 的 87%** → 每轮判超预算 → 每轮 `smartTrimByTokens` 折历史（SHRINK）→ 历史永远不可能成为前缀。改为按字符计（中文 0.9 / 非中文 0.3）。
  4. **尾巴拼进历史 user 消息**（`applyTailDynamicContext`）：本轮带尾巴、落库干净版 → 下轮从该 user 起分叉。改为末尾独立 system 消息（`AGENT_TAIL_CONTEXT_MODE=inline` 可回滚）。
- **额外交付（最大一笔）**：能力域目录从轮内消息迁入 **system 段**（`turn-domain-cards.ts` + `AbstractChatProvider` 注入点，`AGENT_DOMAIN_CARDS_IN_SYSTEM=0` 回滚）。它 8.2k 字符挂在尾部时位置每轮后移，隐式缓存永远命中不了=每轮全价 3,200 token；进 system 后跟 system 一起命中。**踩坑**：语料顺序必须按工具名排序——域卡每域只取前 14 个（位置截断），`visible ∪ deferred` 的先后逐轮变，不排序则同一语料生成不同字节，system 每轮都变，命中率反而从 59% 掉到 26%。

## session-recap 折缓存问题收尾：两处真因（2026-10-22 凌晨第二轮）
- **原提案作废**：我上一轮说「把 recap 挪到尾部」，实测证明方向错了——recap 在尾部意味着**每轮都重付**（它位置逐轮后移，永远进不了前缀），而 index 1 只要字节稳定就是全命中。真正的问题是「recap 在不该变的时候变了」，不是「它在 index 1」。已经用量化数据否掉：尾部方案的每轮成本 > 折叠轮省下的钱。
- **真因 ①（每个折叠周期多断一次缓存）**：`applyEnhancedRecap` 是异步的，LLM 合并完就**原地替换**第 1 条 recap 消息 → 那一轮请求与上一轮在 index 1 分叉。实测（`PREFIX_DEBUG=1` 的 `diffAt`）：改动前每次折叠会断两次（折叠轮 + 1~2 轮后增强落地轮），24 轮里 `diffAt=1` 出现 10 次，而实际只折叠 8 次。修法=`deferredRecapEnhance` 暂存 + 只在折叠点合入（`absorbDeferredRecapEnhance`，按内容键精确移除被吸收的待归纳行，不误删其后新增的）。改后 24 轮 `diffAt=1` = 5 次 = 折叠次数，多余的断点归零。
- **真因 ②（更狠，意外挖到）**：`MAX_CONTEXT_TOKENS=6000` 把 **system 段也算了进去**，而域卡迁进 system 后 system 已 12.8k 字符（估 ≈5-6k）→ 真实长度的对话**每轮都判超预算** → 每轮走 `smartTrimByTokens` → 每轮重建 recap → **每轮都在 index 1 砍前缀**。探针（700 字符/轮）实测：`diffAt=1` 每轮必现、窗口被压到 10 条、命中率 69~74%。修法=预算只算对话段（`systemTokensInBudget()`，`AGENT_TRIM_INCLUDE_SYSTEM=1` 回滚）。
- **A/B（同一二进制，14 轮 × 700 字符，DeepSeek 隐式缓存）**：命中率 71.3% → **76.3%**；每轮 miss 3,395 → 3,022（−11%）；`diffAt=1` 每轮 → 仅 2 次（两次真折叠）；窗口 10 条 → 12 条（原文更全）。按命中价 1/10 折算计费当量 −5.7%。
- 语义/UI：recap 是 system 角色内部消息，**从不进客户端**（`src/ws`、`src/routes` 全无引用），位置也没动，所以这轮无需改 UI；语义上摘要区落后一批由 `[unsummarized]` 原文区承接，信息不丢。
- 契约测试：`test/chat-thread-store.test.ts` 增量摘要用例改为锁定新契约（折叠前不落地 + 折叠时合入 + 被吸收行清出）。回归 41 + 65 全过，tsc 零错误。

## 画像写入时机设计提案（2026-10-22 晚，已保存待评审）
- 文档：`docs/design/user-profile-write-scheduling/2026-10-22-profile-write-scheduling.md`（仅提案，未实施）。

## 安装包对齐 dev 的体积测算（实测本机）
